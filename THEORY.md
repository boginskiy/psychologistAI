# Theory

### Токен

Токен формата:
token = <user ID>:<generators.CreateUUIDv7ToString()>:<user IP>:<user Agent>

#### Критические уязвимости безопасности
Утечка IP-адреса и User-Agent. Вы жестко привязали токен к IP и заголовку браузера. Как только пользователь отключит VPN, переключится с Wi-Fi на мобильный интернет или браузер обновится — его рефреш-токен станет бесполезным куском мусора. Пользователь будет принудительно разлогинен каждые несколько минут. Кроме того, у мобильных операторов динамические IP могут меняться прямо посреди сессии.

Атака перебором (Brute-force) соли. Если злоумышленник получит доступ к вашей базе данных со столбцами user_id, refresh_token_hash и salt, он сможет очень быстро подбирать валидные строки. Поскольку входные данные (ip, user agent) предсказуемы или ограничены, пространство поиска сужается. Современные GPU взламывают одиночный SHA-256 миллиардами попыток в секунду.

Отсутствие механизма отзыва (Revocation). Что произойдет, если телефон пользователя украли? Или вы заметили подозрительную активность? Вам нужно отозвать конкретный рефреш-токен. В вашей схеме единственный способ сделать это — сменить пользователю соль в профиле. Это инвалидирует абсолютно все его устройства сразу (принудительный логаут везде).

Timing Attack (атака по времени). При проверке вы собираете строку, добавляете соль из БД и считаете хеш. Время выполнения операции CreateBytesHashSHA256WithSalt зависит от длины и содержимого строки. Злоумышленник, отправляя разные значения token, может по микросекундной задержке ответа понять, угадал ли он начало правильного токена еще до того, как база данных подтвердит существование пользователя.

Replay Attack (атака повтором). Если ваше приложение работает по HTTP (даже случайно, например, в локальной сети за проксиком), перехватчик трафика может просто скопировать куку целиком. Без жесткого ограничения срока жизни (TTL) в самой базе данных этот токен можно использовать вечно.


token = JWT (Stateless-подход)

Самый надежный и масштабируемый вариант — убрать проверку IP/UA из состава самого токена и переложить её на уровень бизнес-логики, а хранение состояния заменить криптографической подписью.

В классической схеме JWT-авторизации у вас будет два разных токена, каждый со своей четкой ролью.

Access Token (AT) — «пропуск на 5 минут».
Refresh Token (RT) — «дубликат ключа от сейфа», живет долго.

Главное правило: оба они являются JWT, но подписаны разными секретами и содержат разный набор данных.



#### Почему IP и User-Agent нельзя класть в токен

Динамичность. Это главная причина. Пользователь отключил VPN, переключился с домашнего Wi-Fi на мобильный интернет или браузер автоматически обновился. Как только реальный IP или строка User-Agent изменятся хотя бы на один символ, проверка подписи внутри токена пройдет успешно, но ваша логика сравнения «значение из токена == значение из запроса» вернет ошибку. Пользователя выбросит из системы без причины.

Специфика мобильных сетей. У мобильных операторов часто используются целые фермы прокси-адресов. Запрос от одного и того же человека может прилететь то с IP-адреса из Москвы, то из Новосибирска, при этом пользователь просто едет в метро.

Сложность ротации. Если вы захотите обновить (refresh) токен, вам придется заново собирать данные об IP/UA и перевыпускать JWT. Это лишняя нагрузка и точки отказа.

Безопасность через неясность не работает. Если злоумышленник украл токен, он легко узнает ваш фиксированный IP и UA прямо из текста самого JWT (он читается без расшифровки). Зная эти данные, ему будет проще имитировать легитимного пользователя.


#### Главное отличие философии Access Token от Refresh Token

Refresh Token: Хранит данные для управления сессией. Ему нужно знать ID пользователя, чтобы найти его соль/хеш в БД при обновлении.

Access Token: Хранит данные для авторизации запроса. Он должен отвечать на вопрос «Куда пользователю можно ходить?», а не «Кто этот пользователь?» (его личность уже подтверждена рефреш-токеном). Поэтому он должен быть максимально легким.
